## Build these services (ids exactly as given)

Add a `dept` field to every catalog entry: 'sales' | 'market' | 'trust' (company-brief and lead-list are 'sales').

1. **people-map** (sales) "Who to talk to": input {company, goal} (e.g. "selling HR software"). Lead works out which functions matter for the goal; Records finds current people at the company by those functions/titles (peopleAt with several title groups, rank seniority); Field confirms each person on the open web (search "Name Company", snippet must mention surname + company, flag "former/ex-/left"). Deliver 3-8 people with role, why they matter for the goal, confirmation checks. Unit for pricing: 1 map.
2. **competitor-teardown** (market): input {company, focus} . Resolve the company (like company-brief resolve). Records finds 4-6 competitors (companySearch semantic on the company's description, same country optional, exclude itself); Lead screens them with one model call. For each competitor (step per competitor): Records gives headcount/founded/funding from the search fields/enrich; Field reads its homepage (+ /pricing if it exists, via readPages) and extracts positioning one-liner, target customer, pricing (if stated) each with an exact quote verified by quoteOnPage. Then a Writer step produces "how the client differs / where it's exposed" points citing only verified items (reuse the audit idea from company-brief: cites must exist, no hedging words). Unit: 1 teardown.
3. **market-map** (market): input {space, country?, count}. Like lead-list without people: companies in the space with name, domain, headcount, founded, funding, HQ (Records), each confirmed by Field reading its homepage with a quoted line showing what it does (quoteOnPage). Reuse lead-list's search filters, screening and DNS liveness ideas (factor shared helpers into a module if useful, e.g. server/src/services/shared.ts, without breaking lead-list). Unit: per company delivered, like lead-list (partial delivery on budget).
4. **vendor-check** (trust) "Check before you pay": input {company (name or domain), context} e.g. "supplier asking for a 50% deposit". Produce a verdict green / amber / red with evidence. Signals, each a check {name, ok, severity, note, source}: domain resolves and site loads; Records has a company record and it matches the name/domain; founded year and headcount plausible; a named leader exists in the people database AND on the web; web search for complaints/scam/fraud/lawsuit mentions (Field reads snippets, quotes them; an LLM classifies each snippet as about THIS company or not, quote must be in the snippet); news check. The verdict is computed in plain code from the checks (e.g. any high-severity fail → red; 2+ medium → amber), never by an LLM alone. Unit: 1 check.
5. **person-check** (trust) "Verify a person": input {name, company, title?}. Records: person search by name + current employer domain/name → current title, start date, profile URL; Field: web search for the person + company → snippets confirming/contradicting (former/left), plus the company's own team/about page if found. Verdict: confirmed / mismatch / not found, computed in code. Unit: 1 check.

## Output shape (so the web UI can render every service generically)
Every new service returns an object with:
```
{
  headline: string,                       // one-sentence answer, plain words
  verdict?: 'green' | 'amber' | 'red' | 'confirmed' | 'mismatch' | 'not-found',
  facts?: Resolved[],                     // two-angle fact rows (same type as company-brief) when relevant

  points?: { text: string; cites: string[] }[],
  stats: Record<string, number>,          // include counts like verified/checked/conflicts
  csv?: string,
  partial?: boolean, priceUsd?: number
}
```
